# Chonk GRPO on GSM8K: notes on the configs

These notes explain the settings in `chonk-gsm8k-9n-dtensor-vllm-ep4.yaml` (the 9-node run) and `chonk-gsm8k-debug-4n.yaml` (the 4-node debug variant), plus the patches and environment variables the Apertus 2 stack in `backends/nemo-rl/apertus2/` adds. The configs themselves carry no comments; the reasoning lives here.

## What the run is

This is a pipeline test, not a tuned recipe. Chonk (Apertus 2 long-context base, iter 3576) is a 108.3B-parameter MoE with about 8B active parameters per token: 42 layers in a 3:1 KDA-linear/full-attention pattern, 256 routed experts (top-8) in a 1792-wide latent space plus one shared expert. Routed experts are 95% of the weights. We train it with sync GRPO on GSM8K, with the HF modeling code as the trainer (NeMo-RL DTensor v2 / Automodel, FSDP2) and vLLM for generation on a separate node.

Run with `PARTITION=preemptable bash backends/nemo-rl/apertus2/launch.sh experiments/grpo-chonk/chonk-gsm8k-9n-dtensor-vllm-ep4.yaml 9 <run>`. On `preemptable` the launcher submits with `--requeue`, so a preempted job goes back into the queue under the same job ID (job 3660245 was preempted after 70 s and, without it, simply died); `ray.sub` gives each attempt its own `<jobid>-<restart>-logs` directory, and the Slurm output file is appended to rather than overwritten. With checkpointing off, a requeued run starts again from step 0. The debug variant fits the debug partition: `PARTITION=debug JOB_TIME=00:22:00 bash backends/nemo-rl/apertus2/launch.sh experiments/grpo-chonk/chonk-gsm8k-debug-4n.yaml 4 <run>`.

## Node layout and memory

Generation is non-colocated: 8 nodes (32 GPUs) train and 1 node runs vLLM. Eight trainer nodes is the minimum for this trainer. FSDP2 keeps fp32 weights, fp32 gradients and two fp32 AdamW moments, 16 bytes per parameter, so about 1.73 TB, or 54 GB per GPU on 32 GPUs. On top of that come per-layer temporaries that do not shrink with more GPUs: FSDP gathers a whole MoE layer (all 256 experts, about 5.4 GB in bf16) and produces its full gradient (5.4 GB bf16, then a 10.5 GB fp32 reduce-scatter buffer), with the previous layer's buffer often still in flight. The debug run measured about 39 GiB of such temporaries.

That is why `NRL_OFFLOAD_OPTIMIZER_OUTSIDE_STEP=1` is set for the trainer workers. AdamW's state only exists after the first optimizer step, so step 1 fit, but from step 2 on the 25 GiB of state stayed resident through backward and two 9-node runs (3656962, 3657902) ran out of memory on the reduce-scatter buffer. With the flag, the state lives in host memory and is moved to the GPU only around `optimizer.step()`. Values are moved, never converted, so everything stays fp32; the cost is one 25 GiB copy each way per step. Emptying the CUDA cache every micro-batch (`clear_cache_every_n_steps: 1`) was tried first and was not enough: it cut fragmentation from 11.75 to 7.1 GiB but still failed, and slowed training from 57 to 72 s per step. Expandable segments, bf16 gradient reduction and more nodes were ruled out.

The vLLM node holds the bf16 weights (216 GB) split four ways with expert parallelism, about 54 GB per GPU at `gpu_memory_utilization: 0.8`.

## GRPO and data settings

The batch is 16 prompts x 8 rollouts = 128 samples, one optimizer step per GRPO step; with 32 trainer GPUs and micro-batch 1 that is 4 accumulation steps. In the debug variant there are only 12 trainer GPUs, and 128 does not divide by 12, so it uses 6 x 8 = 48 (still 4 per GPU). A full GSM8K epoch at 16 prompts per step is 467 steps.

`reference_policy_kl_penalty: 0` means no KL term. NeMo-RL then skips loading a reference model and skips the reference logprob pass.

Chonk is a base model without a chat format, so the chat template just concatenates text and the five-shot prompt in `gsm8k-five-shot.txt` goes in as is. Generation stops at `Question:` or after 256 tokens; rewards come from NeMo-RL's math environment (math-verify against the number after `####`). The five shots are the first five GSM8K train problems, so they also appear as training prompts, which does not matter for a smoke test. The debug variant validates on 32 problems from the GSM8K test split; `GSM8KDataset` ignores `split_validation_size`, so the validation set has to be configured explicitly.

The learning rate is NeMo-RL's default for its 1B example (AdamW 5e-6, warmup from 0.1x over 50 steps). In a 5-step run it never exceeds 8.6e-7, so it does not matter here, but 5e-6 is high for a real run at this scale (DAPO used 1e-6 for a 32B model).

## Trainer settings

`force_hf: true` uses the HF remote code (`modeling_apertus2.py` from swiss-ai/hfconverter), because Automodel has no native Apertus 2 implementation. `attn_implementation: sdpa` because the image has no flash-attn, which also rules out sequence packing. Activation checkpointing is on for all 42 layers; with one sequence of at most 1280 tokens per micro-batch the saved activations are well under a GB, so the temporaries above dominate memory, not activations.

`FLA_FLASH_KDA=0` is set for the trainer workers only. fla routes `chunk_kda` calls made without gradients (the logprob pass) to its FlashKDA kernel, which requires a bf16 `beta`, while the HF code passes fp32 (job 3656748 failed with `beta must be bfloat16`). The training pass uses fla's Triton kernels anyway, so this also keeps the logprob and training passes on the same kernels.

The experts already run as a grouped matmul: the HF expert class carries `@use_experts_implementation`, and transformers 5.17 picks `grouped_mm` by default.

## Generation settings

Chonk has 7 KV heads, so vLLM tensor parallelism must be 1 (7 is the only other divisor). The engine therefore uses expert parallelism 4 within the node, which vLLM runs as data parallelism 4 for attention. `load_format: dummy` because the weights arrive through the refit before the first generation.

`async_engine: true` is required. With the sync engine, data-parallel ranks that finished their prompts stopped stepping while the others waited on them in the MoE collectives, and job 3655556 hung mid-generation for half an hour. This is the same failure as Andres's Megatron-trainer run (job 5003401, "Gloo DP timeout"), whose config also used the sync engine. The async engine uses vLLM's serving-style data parallelism, which keeps idle ranks stepping.

## Environment (EDF)

`HF_DEACTIVATE_ASYNC_LOAD=1`: transformers 5.17 queues every checkpoint tensor on a thread pool that copies them into host memory as fp32 faster than the loader consumes them, and with four trainer ranks per node that ran a node out of host memory (job 3655185). With the Automodel patch below that skips the transformers load, this mostly matters as a safeguard.

`TRITON_CACHE_DIR` points at iopsstor so compiled Triton kernels (fla KDA, vLLM) survive between jobs. With node-local `/tmp`, every job recompiled them during the first generation (validation took 86 s cold versus 29 s warm). It must not be on the NFS home, which gives stale-file-handle errors.

`pydeps.sh` installs `nemo-lens` and `soundfile` into the runtime overlay, since NeMo-RL imports both at module level and the image lacks them.

## Patches

Automodel (applied to the working tree by `setup.sh`, HEAD stays at the pin):

- `0001-sharded-hf-safetensors-load`: the HF checkpoint stores one key per expert, while the HF module holds stacked `gate_up_proj [256, 3840, 1792]` / `down_proj [256, 1792, 1920]`. Automodel only merges per-expert keys for model types on a hardcoded list, and loads with `strict=False`, so the experts would silently stay random. The patch replaces the post-shard load with a rank-local one: each rank reads only its shard of each tensor from the safetensors files (about 1/32 of the checkpoint), copies it into its parameter, and stacks the per-expert keys for its own experts. Loading takes 8-26 s and prints `[hf-sharded-load]` progress; `check_env.sh` runs the same name mapping against the shard headers.
- `0002-skip-discarded-hf-load-under-meta-init`: with `force_hf`, Automodel called transformers' `from_pretrained` on every rank inside an empty-weights context, so each rank read the whole 216 GB checkpoint and threw it away before the real load (3-7 minutes). Under meta init the model is now built from its config instead.

NeMo-RL (committed in the clone, applied with `git am` by `setup.sh`):

- `0001-refit-keep-Apertus-2-qb_beta-in-fp32`: the quantile-balancing router offsets are an fp32 buffer that FSDP2 does not cast, so the trainer routes with fp32 values; the refit sent them in bf16.
- `0002-dtensor-v2-optionally-keep-optimizer-state-on-CPU-ou…`: the `NRL_OFFLOAD_OPTIMIZER_OUTSIDE_STEP` switch described above.
- `0003-dtensor-v2-reuse-pinned-host-buffers-for-the-offload`: in its first version the switch moved the state with plain `.to()` every step, allocating fresh host memory each time. In job 3661568 step 2 then fit in memory (reward 0.48, generation KL error 0.0006), but its training phase took 658 s instead of 63 s: the ranks finished the optimizer phase up to 10 minutes apart, and the fast ones hit NCCL's 10-minute timeout in the statistics all-reduce after the step, which killed the run. Now the host copies are pinned buffers allocated on the first offload and reused, the copies are asynchronous, the CUDA cache is emptied once per step before the state comes back, and each step prints `[optimizer-offload] rank R: to GPU …s, step …s, to CPU …s` (rank 0 always, other ranks when they take over 10 s).

## Results so far

The debug variant reaches the initial validation (accuracy 0.31-0.47 on 32 test problems at temperature 1.0) and then runs out of memory in training, as expected on 12 GPUs. On 9 nodes, step 1 completes: reward 0.48-0.61, generation KL error 0.0005-0.0007 (vLLM and trainer logprobs agree, so the bf16 router autocast in the trainer is not a visible problem), about 120-137 s per step (training 57-72 s, generation 35 s, refit 14 s, logprobs 11 s). Step 2 ran out of memory before the optimizer-offload switch was added. With the switch it fit, but the slow state moves described under patch 0003 ended the run. With patch 0003, job 3664589 completed all five steps and exited cleanly (2026-10-14, 13 minutes from start to exit). Rewards were 0.53, 0.45, 0.48, 0.38 and 0.49 (16 prompts per step, so noisy; the learning rate is still below 1e-6 in warmup), generation KL error 0.0005-0.0006 throughout. Step 1 took 118 s; steps 2-5 took 93-95 s each (training 40-41 s, generation about 30 s, refit 10 s, logprobs 9 s). The offload costs about 1.5 s per step on rank 0 (state to GPU 1.0 s, step 0.3 s, back to CPU 0.3 s); the first offload, which allocates the pinned buffers, took 1.7-3.3 s. The tracebacks at the end of the log come from vLLM and the math environment being torn down at shutdown.

## Full-epoch run

`chonk-gsm8k-9n-dtensor-128x16.yaml` is the first run meant to go to the end rather than test the pipeline. Each GRPO step generates 128 prompts x 16 rollouts = 2048 samples and trains on them in four optimizer steps of 512 (`train_global_batch_size: 512`, 16 micro-batches per GPU each). With a single optimizer step per rollout batch the PPO ratio between the current policy and the policy that produced the logprobs is exactly 1 (NeMo-RL recomputes the old logprobs with the trainer before training), so the clipping never acts and the update is a plain policy gradient; with four minibatches the later ones are slightly off-policy and the ratio and its clipping matter, as in DAPO (which used 16 minibatches per rollout batch). One epoch of GSM8K train is 7473 / 128 = 58 GRPO steps, 232 optimizer steps. The learning rate is 1e-6 with a linear warmup from 1e-7; NeMo-RL steps the scheduler once per GRPO step, not per optimizer step, so the warmup is 6 GRPO steps (10% of the run). This is sync GRPO: generation and training alternate, and `async_engine: true` only changes how vLLM runs its data-parallel ranks. NeMo-RL's separate importance-sampling correction for the vLLM-versus-trainer mismatch (`use_importance_sampling_correction`) is off; the measured generation KL error is 0.0005-0.0006. Validation runs on the whole GSM8K test split (1319 problems, one sample each at temperature 1.0) at the start, every 3 GRPO steps and at the end. TensorBoard logging is on, under the run's log directory.

Checkpoints are saved every 21 GRPO steps (it was 3 at first; 21 is a multiple of the validation period, so every checkpoint has a validation accuracy to rank it by) and at the last step, so that a preempted or time-limited job resumes instead of starting over: a requeue (same job ID) or a resubmission with the same run name picks up the latest checkpoint in `results/<run>`. A checkpoint holds the fp32 weights and both AdamW moments, about 1.3 TB. `keep_top_k: 1` keeps the best one by validation accuracy plus the latest, so at most about 2.6 TB stay on disk. `checkpoint_must_save_by` makes the run save and stop 30 minutes before the 24-hour limit of the `preemptable` partition. Extrapolating from the 128-sample steps, a GRPO step takes about 16 minutes (training about 11, logprobs 2.5, generation about 3, weight sync 10 s), so the epoch takes roughly 17 hours with validation and saves if it is never preempted; every preemption loses at most 21 GRPO steps (about 3 hours with micro-batch 2). Saving and resuming had not been tested before this run; the first saves, at GRPO step 3 of jobs 3664705 and 3664728, wrote 1.2 TB in about 42 s.

`chonk-gsm8k-9n-dtensor-128x16-mb2.yaml` is the same run with `train_micro_batch_size: 2`. Training dominates the step, and FSDP gathers every layer's full weights (all 256 experts) and reduce-scatters its gradient once per micro-batch, so two sequences per micro-batch should pay that communication half as often per sample. The gradients are the same (NeMo-RL normalizes the loss over the whole global batch); the cost is a little more activation and logit memory (the fp32 logits of two 1280-token sequences over the 200k vocabulary are about 2 GB). Measured (job 3664728 against the micro-batch-1 job 3664705): training per GRPO step fell from about 605 s to 315 s and the step from 830 s to 535 s, with the same validation accuracy so far (0.50 at step 3 in both). The halving confirms that the per-micro-batch communication, not the compute, sets the training time. At micro-batch 2 the step is about 60% training, 27% logprob recomputation (143 s) and 12% generation (64 s); the reference logprobs are already skipped because the KL penalty is 0.

`chonk-gsm8k-9n-dtensor-128x16-mb4.yaml` goes one step further, with `train_micro_batch_size: 4` and `logprob_batch_size: 8`. The logprob pass ran one sequence at a time and pays the same per-pass weight gathers as training; it is forward-only, so it has room for larger batches. GSM8K sequences are short (generations average about 90 tokens), so activation and logit memory stay small unless a batch catches a sequence near the 1280-token limit, where the fp32 logits of four sequences are about 4 GB in training and eight about 8 GB in the logprob pass. The expected step is about 270 s if both passes halve again. Untested; GPU memory peaks at micro-batch 2 were not logged.

`chonk-gsm8k-9n-dtensor-128x16-mb8.yaml` doubles both again (`train_micro_batch_size: 8`, `logprob_batch_size: 16`). Each GPU sees 16 sequences per optimizer step (512 over 32 GPUs), so micro-batch 8 means two micro-batches per optimizer step and 16 would be the limit. The measurements give about 9.5 s per training micro-batch and 2.2 s per logprob batch, almost all of it weight gathers, so the expected step is about 80 s of training, 10 s of logprobs and 64 s of generation, roughly 165 s. The worst case for memory is a micro-batch padded to the 1280-token limit: about 8 GB of fp32 logits in training (more with their gradients) and 16 GB in the logprob pass. Untested.

`chonk-gsm8k-9n-dtensor-128x16-async.yaml` adds NeMo-RL's async GRPO on top of the micro-batch-2 run: a background collector keeps generating with the latest weights it has while the trainer trains, and trajectories may be at most one training step old (`max_trajectory_age_steps: 1`). Because the trajectories then come from an older policy than the one whose logprobs the trainer recomputes, NeMo-RL's guide requires the importance-sampling correction, the per-token ratio between the trainer's old logprobs and the generator's logprobs; it is truncated at 2 (TIS) so a few tokens with a large ratio cannot dominate the update. The generator and trainer already sit on separate nodes and vLLM already runs its async engine, which are the other two requirements. The gain is bounded by the generation time that can be hidden behind training, about 64 s per step as measured at micro-batch 2 (12% of that step, closer to a quarter if the micro-batch-4 step reaches about 270 s). Untested.

## Megatron trainer variant

`chonk-gsm8k-9n-megatron-vllm-ep4.yaml` swaps the trainer for Megatron (NeMo-RL's Megatron policy worker with Megatron-Bridge) and keeps everything else from the HF config: the same 8 + 1 nodes, GRPO and data settings, vLLM node and KL 0. Run it the same way, with `chonk-gsm8k-debug-5n-megatron.yaml` (4 + 1 nodes) as its debug variant. It follows the Megatron-trainer + vLLM example of alps-extended-images#64, which completed two GRPO steps on 16 trainer + 8 vLLM nodes (job 5045801, a smoke test without numerical checks). The sources are the same as there: the NeMo-RL clone plus swiss-ai/Nemo-RL PR #8, Megatron-LM-MoE at the head of PR #88 and Megatron-Bridge at the head of PR #5 (Apertus2 provider and checkpoint conversion). The image ships neither Megatron-Core nor Megatron-Bridge, so `setup.sh` checks both out next to the NeMo-RL clone and the EDF puts them on `PYTHONPATH`. The HF path is untouched; the Automodel and DTensor patches simply play no part in this one.

Layout: no pipeline parallelism and expert parallel 32, so each GPU holds 8 of the 256 experts of every layer plus a full copy of the non-expert weights (about 5B parameters: embedding, output layer, attention, shared experts, latent projections). The first version used pipeline 2 (20 + 22 layers) with expert parallel 16, following Andres's pipeline 4 / expert parallel 16 example, but every pipeline-parallel debug run hung in the first refit (see below), so the layout dropped pipeline parallelism. With 32 GPUs, pipeline 1 rules out expert parallel 16: the remaining factor of 2 would become expert data parallelism, two copies of every expert, about 73 GB per GPU of weights and gradients before activations. With expert parallel 32 every expert still lives on exactly one GPU (about 3.6B parameters each). Unlike FSDP, expert parallelism never gathers a whole layer or builds its full gradient, which removes the per-layer temporaries that dominated the HF trainer.

Memory: Megatron keeps bf16 weights for compute, fp32 gradients (`grad_reduce_in_fp32: true`, so no bf16 reduction) and, in the optimizer, fp32 master weights plus the two AdamW moments, so updates are fp32 as in the HF run. Each expert has a single owner, so the optimizer cannot shard expert state across GPUs, and with AdamW on the GPU that adds up to an estimated 80 GB per GPU before activations. `optimizer_cpu_offload: true` with fraction 1.0 therefore keeps the master weights and moments in host memory and runs the AdamW step on the CPU (Megatron's own `HybridDeviceOptimizer`, used the same way by NeMo-RL's GLM recipes). That leaves about 52 GB per GPU of weights and gradients (it was 38 GB with pipeline 2, which also split the non-expert weights), plus activations (activation checkpointing stays off), and roughly 60 GB of host memory per rank, 250 GB per node, since the expert state dominates the optimizer either way. The grad-reduce and param-gather overlaps are off, as in those recipes.

Optimizer and schedule match the HF run: AdamW, lr 5e-6, weight decay 0.01, betas (0.9, 0.999), warmup from 5e-7 over 50 steps, then constant. Differences from Andres's recipe: AdamW instead of MuonMD; no FP8 experts and no expert offloading (in the fork, coarse offloading requires FP8 expert compute, which would no longer match vLLM's bf16 weights); no `expandable_segments`.

Router: NeMo-RL freezes the router weights by default (`freeze_moe_router`), and `moe_router_quantile_balancing_freeze` keeps the checkpoint's `qb_beta` routing offsets fixed (no quantile statistics, no bias update). This differs from the HF run, where the router weights train. Andres's config set the QB freeze as a top-level `megatron_cfg` key, which this NeMo-RL version ignores, so here it goes through `model_overrides`.

Dispatch and refit: tokens move between expert ranks with the `flex` dispatcher over the image's UCCL-backed DeepEP, with the UCCL settings of the pretraining run; refit goes through Bridge's weight conversion with the small refit buffers of the example (`NRL_REFIT_BUFFER_MEMORY_RATIO=0.005`). Bridge's config loader takes a file lock in `~/.cache` by default, which is the NFS home; `MEGATRON_CONFIG_LOCK_DIR` in the EDF moves it to node-local `/tmp`.

Checkpoint conversion: on the first run, Bridge converts the HF checkpoint to Megatron's distributed format under `$HF_HOME/nemo_rl/` on iopsstor, and later runs (any layout) reuse it. The conversion runs inside the job, using the job's own parallel layout. The iopsstor purge can remove it, after which the next run converts again.

Megatron-LM patch (applied to the checkout's working tree by `setup.sh`, HEAD stays at the pin): `0001-distrib-optimizer-detach-fp32-param-shards`. The distributed optimizer takes each fp32 parameter's shard as a plain view of the parameter, so the shard is a non-leaf tensor in the autograd graph. The GPU optimizer never notices, because its parameter groups are assigned directly, but the CPU-offload optimizer is rebuilt through `torch.optim.Optimizer`, which rejects non-leaf tensors. Chonk has fp32 parameters (the KDA decay parameters `A_log` and `dt_bias`, which the Bridge provider keeps in fp32), so the first Megatron debug run (3662462) failed at optimizer creation with `can't optimize a non-leaf Tensor`. The patch detaches the view, as the same function already does for bf16 parameters; it still shares storage, so optimizer updates still land in the parameter.

Megatron-LM patch `0002-distrib-optimizer-index-params-in-optimizer-order` (written after the first Megatron checkpoint saves failed; not yet verified by a run). Saving failed in the resume test (3665320) and at step 21 of the async run (3665272) with `AssertionError: (torch.Size([1120]), 7802168, 7805752)` in `sharded_param_state_dp_reshardable`: the state looked up for a 3584-element parameter shard belonged to a 1120-element one. The distributed optimizer records each parameter's position in its optimizer group in gradient-buffer order, but builds the optimizer's groups with all fp32 shards first and the bf16 ones after. With only bf16 parameters the two orders agree, which is why upstream never notices; Chonk's fp32 parameters (`A_log`, `dt_bias`, `qb_beta`) sit between bf16 ones, so the checkpoint code fetched the wrong parameter's state. Training is unaffected, because the optimizer step uses the groups directly. The patch rebuilds the position map in the optimizer's order. Every Megatron run started before it fails at its first save.

Patch 0002 works for saving: the resume test's first half (3665525) saved a 1.4 TB checkpoint. Loading it (3665526) then failed in the CPU-offload optimizer with a `KeyError` on an fp32 tensor: after loading, `HybridDeviceOptimizer` copies each parameter's saved master weights into its fp32 copy, looked up in a map that only holds the fp32 clones made for bf16 parameters. Megatron-LM patch `0003-hybrid-optimizer-load-master-into-inner-param` looks the target up in the map of all inner parameters instead, which for an fp32 parameter is its CPU copy. Not yet verified; the step-2 checkpoint of `chonk-mcore-resume2` is still there to test it.

Overnight runs of 2026-10-15 (all with packing at 5120 tokens per micro-batch, final-checkpoint only): sync 128x16 (3665522) and both 128x32 runs (3665523, 3665524) ran out of GPU memory in their first training step, when NCCL allocated buffers for the data-parallel group (`Cuda failure 2 'out of memory'` under `ncclUnhandledCudaError`). After model setup each trainer GPU already holds about 63.5 GB (weights, gradients, DeepEP buffers), and a 5120-token micro-batch with its 200k-vocabulary logits fills most of the rest; the earlier packed run (3665319) got through 20 steps with the same settings, so the margin is small. The packing budget of the 1280-token runs is now 4096 tokens per micro-batch (the 4K configuration keeps 5120, the minimum for a 5120-token sample). The async 128x16 run (3665521) completed two steps and then hung in a DeepEP dispatch in step 3 until UCCL's CPU timeout of 6000 s ended it; the cause is unknown, and the timeout is now 1200 s so that a hang ends sooner. The 4K async run (3665723) failed in the first logprob pass with `CUDA error: an illegal memory access`, surfacing when the logits are converted to fp32; the sync 4K run (3665311) had passed the same pass for five steps, so this is unexplained and may not reproduce. Only one of 32 trainer ranks (rank 24) faulted, on nodes no other job had just used. The error is reported where it is noticed, not where it happens (CUDA kernels run asynchronously), so the logs do not name the faulting kernel. The 4K async configuration therefore asks the CUDA driver for a GPU core dump on the fault (`CUDA_ENABLE_COREDUMP_ON_EXCEPTION`, lightweight: no memory contents, written to `nemo-rl/coredumps/`, the process still fails normally); `cuda-gdb` on the dump names the kernel and its arguments. The run also changed to a total length of 4096 tokens, so if the fault depends on sequence length it may not recur.

Runs of the night to 2026-10-16 (packing at 4096 tokens per micro-batch). The sync 128x16 run (3669035) completed the epoch in 2 h 42 min: about 125 s per GRPO step (generation 70 s, training 42 s) and about 195 s on validation steps; GSM8K test accuracy went from 0.466 at the start to 0.89-0.90 from step 33 on (0.894 at the end). The async runs all failed: the 128x32 async run (3669036) after 10 steps with `illegal memory access` in the logprob pass (the same place as the 4K run's failure), the 128x32 gbs-1024 run (3669037) in step 1 with an NCCL CUDA error while creating a communicator during gradient finalisation (no message; probably memory again), and the 128x16 async run (3669034) after 2 steps when a vLLM data-parallel rank stopped exchanging with the others (Gloo receive timeout after 30 min) and the job then sat until its 5-hour limit. Across all runs so far, async with packing failed every time (four runs, within 1-10 steps, both failures in the logprob pass coming right after a weight sync), while sync with packing ran 58 and 20 steps and async without packing ran 21; the cause is not known. The 4K async run (3668998) never started: its configuration file had been left with stray duplicated lines and did not parse. The resume test (3669038) loaded the optimizer state, so patch 0003 works, and then stopped at Megatron's scheduler check because part B asked for 4 steps instead of 2 (NeMo-RL derives the scheduler's length from `grpo.max_num_steps`); a resume with an unchanged configuration, as after a preemption, does not hit this. GPU core dumps on faults (`CUDA_ENABLE_COREDUMP_ON_EXCEPTION`) are now enabled for all Megatron runs.

Debugging setup (2026-10-16). Every Megatron run now records enough to diagnose a crash or hang after the fact:
- GPU core dumps: on an illegal memory access or other GPU exception, the CUDA driver writes `core_<host>_<pid>` (trainer) or `core_vllm_<host>_<pid>` into the run's log directory (`logs/<run>/`), without memory contents. `cuda-gdb -batch -ex "target cudacore <file>" -ex "info cuda kernels" -ex bt` inside the container names the faulting kernel and its call stack. This is needed because CUDA kernels run asynchronously: the Python traceback shows where the error was noticed (in both failures, converting the logits to fp32), not the kernel that faulted.
- NCCL warnings (`NCCL_DEBUG=WARN`) on trainer and vLLM workers, so "unhandled cuda error" comes with the failing CUDA call (for example an out-of-memory `cudaMalloc`); C++ stack traces in PyTorch errors (`TORCH_SHOW_CPP_STACKTRACES`); and the NCCL flight recorder, which on a collective timeout writes each trainer rank's last 2000 collectives to `logs/<run>/fr-rank<N>` (read with `torchfrtrace`).
- Hang dumps: `backends/nemo-rl/hang_watch.sh`, started on every node by `numa_watch.sh`, checks the Ray driver log once a minute; when it has not changed for 15 minutes it writes the Python and native stacks of every process on the node (`py-spy dump --native`) plus GPU utilisation to `slurm/<job>-logs/stacks/<node>-<time>.txt`, and repeats every 15 minutes while the job stays stuck. For the vLLM hang of 3669034 this would have shown what the other three engines were doing while engine 1 waited for them.
- Config check before submission: `launch.sh` runs `backends/nemo-rl/preflight.sh` on the login node (yq): it parses every file of the `defaults` chain, merges them with the command-line overrides, writes the run's key settings (nodes, parallelism, batch and optimizer steps, lengths and packing budgets, async settings, loss, checkpointing) to `slurm/<jobid>-<run>.preflight.txt` (the terminal only shows errors and warnings) and refuses to submit on a parse error, a packing budget below the maximum sequence length, a batch that does not divide the samples per step, async without importance-sampling correction or the async engine, different refit chunk settings for trainer and vLLM, or a save-and-stop deadline after the job's time limit. `PREFLIGHT=0` skips it.

What is known about the two failure types so far. The illegal memory accesses (4K async at step 1, 128x32 async at step 10) both happened in the logprob pass that directly follows a weight sync, on a single trainer rank. The call order is the same in sync and async GRPO (train, weight sync, prepare for logprobs, logprob pass); the difference is that sync generates for minutes between the weight sync and the logprob pass, while async starts the logprob pass immediately. `prepare_for_lp_inference` frees the gradient buffers' GPU memory (`offload_to_cpu` resizes their storage to zero) right before that pass, and the pass then reuses the memory, so any GPU work from training or the weight sync still touching it would fault exactly there. This is a candidate, not a finding; the core dump will name the kernel. The vLLM hang (3669034): at step 2, with collection paused while the buffer was full, engine 1 ran a dummy batch (what an idle data-parallel engine does to keep its expert-parallel collectives in step with busy ones) and waited 30 minutes for the other engines, which had logged nothing since 03:10 and were apparently idle; the job then sat until its time limit. That points at vLLM's coordination of which engines are running, under NeMo-RL's pausing of collection, but the stacks of the other engines are needed to know.

Runs of 2026-10-16 afternoon, the first with the debugging setup. The async 128x16 run (3673680) reached step 16 (test accuracy 0.830 at step 15, about 66 s per step without validation against 125 s sync) and the 4K async run (3673653) ran 50 steps (0.891 at step 40) until it was preempted; with only a final checkpoint it restarted from scratch and failed at step 13. Both failures were again an illegal memory access in the logprob pass on a single trainer rank, and both wrote GPU core dumps. The two dumps agree exactly: a `Warp MMU Fault` in UCCL's internode `combine` kernel (the step that returns the expert outputs to their tokens; `uccl::internode::combine<true, 8, bf16, ...>`), at the same instruction, the load of an entry of `d2h_channel_addrs`, the table of the queues through which the kernel hands RDMA work to UCCL's CPU proxy threads, followed by the read of the queue handle it points to. That table and the handles are allocated once per DeepEP buffer with `cudaMallocManaged` and freed only when the buffer is destroyed, and Megatron creates the buffer once and never replaces it (`fused_a2a.get_buffer`; the hidden size is fixed). So the fault is in UCCL's communication path, not in the packing or logprob code that the Python tracebacks pointed at, and the earlier grad-buffer candidate is unlikely (that memory comes from PyTorch's allocator, the table does not). The registers of the faulting thread narrow it down further: the table index was in range in both dumps (21 and 5 of 32 entries), and the destination register of the table load held zero. The kernel's indexing is therefore fine. (Correction, 2026-10-17: `$errorpc` is the table load itself, while the instruction that dereferences the loaded handle had not executed yet, so the fault is the table read: the GPU could not access the table's page. The zero is what the failed load left in the register, not a null handle read from the table.) UCCL's Slingshot (CXI) transport, which these runs use, was added upstream in June 2026 (uccl#997) and got a fencing fix in July (uccl#998, quiet all CXI proxy queues before buffer reuse); the image builds UCCL at commit 540cc775 (2026-10-05, reports itself as 0.1.1), which includes both. As of 2026-10-17 nothing upstream addresses this: UCCL main is four commits ahead (P2P and GIN only, no EP changes) and has no matching issue or pull request; Megatron-LM-MoE #88, Megatron-Bridge #5 and the NeMo-RL fork's pull requests have no commits since our pins; and the validated Chonk recipes in alps-extended-images #64 are all synchronous GRPO without sequence packing, so async with UCCL has probably not been run elsewhere. Mapping the faulting instructions to the source at that commit: the kernel was posting a network transfer (`nvshmemi_ibgda_put_nbi_warp` or `nvshmemi_ibgda_amo_nonfetch_add` in `ep/include/uccl_ibgda.cuh`), which picks one of the 32 queues from the expert slot (slots 22 and 20 in the two dumps, giving queues 21 and 5), loads that queue's handle from the table, and increments the queue head held in the handle (`FifoDeviceHandle::push`). The fault is at the table load: the handle came back null or could not be read. The table and the handles are allocated with `cudaMallocManaged` (`ep/src/uccl_ep.cc`, Buffer constructor) and prefetched to the GPU; apart from one atomic buffer in the proxy, everything else UCCL uses is ordinary device or pinned host memory. Managed memory is the one kind the CUDA driver may move off the GPU when device memory runs out, and these GPUs run at the limit: each GPU's HBM is a 95 GiB NUMA node, and the memory monitor shows peaks of 92-95 GiB in every Megatron run, crashed or clean. At each of the four illegal-memory crashes, the faulting rank's GPU was the one at 92-95 GiB in the last sample (GPU1 for rank 1, GPU0 for ranks 20, 20 and 24), while the others fell back as their processes exited. Working hypothesis, not proven: with HBM full, the driver evicts UCCL's managed queue table and occasionally cannot service the GPU's next access to it. Two tests separate this from a UCCL logic bug: the all-to-all run (no UCCL at all) and `-async-pack2k` (UCCL as before, with 2048-token packs instead of 4096 to lower peak memory, possible now that the total length is 2048). If memory pressure is the trigger, the fix is either more headroom or a UCCL change that allocates the table with plain `cudaMalloc`. Running the async configuration with Megatron's NCCL all-to-all dispatcher instead of UCCL would confirm the attribution.

On 2026-10-17 the 128x16 base configuration (and everything that inherits from it) was aligned with the target GRPO specification: the advantage is now (R - group mean) / (group std + 1e-6) over all 16 samples of a prompt (`use_leave_one_out_baseline: false`; NeMo-RL's std is the Bessel-corrected one, as `torch.std` in verl), the PPO loss has dual clipping at c = 3.0 (`ratio_clip_c`), and the length limits are 2048 for both the total (prompt included) and the new tokens, up from 1280 and 256, so a response ends at 2048 minus its prompt length (about 1400-1500 tokens with the five-shot prompt). To find out why the table entry reads as zero, the 4K configuration (still on UCCL, with 4096-token logprob packs, the conditions of two earlier crashes) now writes full GPU core dumps for the trainer: `CUDA_COREDUMP_GENERATION_FLAGS` without `skip_global_memory`, so a crash dumps the faulting process's whole device memory (about 70-95 GB, written only on a crash, with progress messages from `CUDA_COREDUMP_SHOW_PROGRESS`). It validates and saves every 20 steps, like the 2k runs, so a preemption no longer loses the whole run. `read_coredump.sh` now also reads the kernel's parameters from constant bank 0 (from 0x210; mapping `combine`'s signature puts `d2h_channel_addrs` at 0x2b0, which is what the faulting instruction loads, and `num_d2h_channel_addrs` at 0x2b8, matching R9 = 32 in the earlier dumps) and the registers of every warp on the faulting SM, then reads the table at that pointer and the handle objects it points to. cuda-gdb 13.3 reads kernel parameters as `(@parameter T *) <absolute bank offset>`, e.g. `x/1gx (@parameter unsigned long *) 0x2b0` (`@param` and `@const` are not accepted). Even the lightweight dump of 3682994 has them: the table pointer was `0x404a20000600`, followed by 32 at 0x2b8. That is exactly where UCCL's start-up allocation puts the table (the 32 handle objects, 32 x 40 bytes rounded to 0x600, come first in a fresh managed block at `0x404a20000000`, the table right after), so the kernel was handed the correct table (all three crashes, in three jobs, show the same pointer and neighbouring UCCL pointers), and the fault is the GPU failing to access that page. The table is managed memory, the one kind the driver may evict from a full GPU and must fault back in; the crashes all fall in the logprob pass, the memory peak (about 95 of 95 GiB), so a failed fault-back under memory pressure is the leading explanation, not yet proven. The NVIDIA driver logs each such fault as Xid 31 with the faulting address and fault type, but the kernel log is readable only by CSCS admins (crashes: nid006992 2026-10-16 ~16:56, nid007533 2026-10-16 ~21:00, nid006285 2026-10-17 ~15:20). If confirmed, the fix is a small UCCL change that allocates the table with `cudaMalloc` and copies it in, which needs a UCCL rebuild. With global memory in the dump this separates the remaining explanations: intact entries (32 addresses one handle object apart, next to the table, which is allocated right after the handle objects) mean the kernel was handed a wrong table pointer; an unreadable page means the table was freed or unmapped; a readable table of zeros or partial zeros means it was overwritten, and what sits around it may show by what.

`preflight.sh` now reports the generation layout and checks it (EP must divide the generation data-parallel size, DeepEP only with the flex dispatcher, raw log-probs with importance correction, matching refit settings when `mcore_generation_config.env_vars` replaces the trainer's).

`chonk-gsm8k-20n-megatron-128x16-2k-async-md.yaml` (vLLM) and `-mcoregen-md.yaml` (Megatron inference) run the 2k configurations with `md_decoupling`, the Muon-style optimizer with hypersphere-normalised matrices and learnable gains that Chonk was pretrained with, at lr 2e-7 (AdamW part: norms, biases and other non-matrix parameters), matrix lr 5e-6 and gains lr 2e-7. Both list two `defaults`: their AdamW parent, then `trainer-16n-ep64-md-decoupling.yaml`, which holds only the trainer changes; NeMo-RL resolves each parent on its own and merges them in order, so the optimizer block applies to either generation backend without copying it (`preflight.sh` now resolves `defaults` the same way). The remaining optimizer settings are Andres's from alps-extended-images #64, which follow the pretraining script: hypersphere projection per row with the initial radius kept, softplus row-and-column gains, polar-express orthogonalisation with shape-based scaling, momentum 0.95 with Nesterov, Adam betas 0.9/0.95, no weight decay; `min_lr` is 0 because the schedule is constant and Megatron's scheduler rejects a minimum above the 2e-7 maximum. The optimizer cannot use CPU offload: Megatron's offload (`HybridDeviceOptimizer`) only implements Adam and SGD, and `md_decoupling` builds its optimizer outside that path, keeping its fp32 master weights and momentum on the GPU and sharding them layer-wise (whole matrices per data-parallel rank, since the orthogonalisation needs complete matrices) instead of with Megatron's distributed optimizer. Expert state is only sharded across ranks holding the same experts, of which there are none at EP32 on 32 GPUs, so on 8 trainer nodes each GPU would hold about 26 GiB more than today (3.2B expert parameters at 8 bytes) on top of a trainer that already peaks near the 95 GiB limit. The trainer therefore runs on 16 nodes with expert parallel 64 (4 experts per GPU, 20 nodes per run): bf16 weights about 13 GiB, fp32 gradients about 26 GiB, optimizer state about 13 GiB, roughly the static footprint of the 8-node AdamW trainer. `offload_optimizer_for_logprob` moves the momentum to CPU around each logprob pass, as in Andres's example. The trainer's `[gpumem]` lines show why: after the save, PyTorch kept 6.5-11.5 GiB more allocated than at the same points of every other step (rank 14: 37.7 instead of 26.1 GiB after logprob preparation, 59.1 instead of 52.5 before training), while the memory outside PyTorch (NCCL, UCCL, CUDA context, about 12-13 GiB) was unchanged, and a run resumed from that checkpoint trained 17 steps without the problem. NCCL logs the failing CUDA call on the worker, but Ray's log deduplication folded those lines away, so the cause is not recorded; an out-of-memory `cudaMalloc` while setting up the communicator is the likeliest reading given the margin. `launch.sh` now sets `RAY_DEDUP_LOGS=0` for the driver, so every rank's lines (errors and `[gpumem]`) reach the driver log. `driver_retry.sh` now also retries an attempt that completed no step when an earlier attempt in the allocation did or the run already has a checkpoint, so a resumed run that fails in its first step is restarted instead of ending the job. These `md_decoupling` runs used the default image; the UCCL fix (uccl patch 0001, D2H handle table in plain device memory) is only in the `nemo-rl-apertus2-ucclfix` EDF, which explains the illegal memory access in 3685049. Fused linear logprobs, which would avoid the full-vocabulary logits, are rejected by NeMo-RL with sequence packing in GRPO; bf16 gradients would save more but change the numerics against the AdamW runs.

The truncated dump is still readable with `readelf` and `xxd`, without cuda-gdb. The section headers sit at the start of the file, and every section except device memory was written: warp state, registers, backtraces, the grid table and the kernel parameters. Only 171 of the 945 memory sections fit in the 5.6 GB. The kernel parameters (`.cudbg.param.dev0.grid0`, which holds constant bank 0 from 0x210) show the table pointer at 0x2b0 as `0x404a40000600` and the count at 0x2b8 as 32. That is again the correct table, just at a different address in this process. The dump marks managed memory with its own section type (`LOUSER+0x1`; device memory is `LOUSER+0x2`). Each of the four processes on the node has exactly one managed section: UCCL's 2 MB block, at `0x404a40000000` in the faulting process. So at the fault the table was still allocated, and the kernel was handed the right pointer to it; it was neither freed nor replaced. Its contents were not captured, because that section starts 28 GB into the file. The explanation that fits is eviction. Memory from `cudaMalloc`, which is everything PyTorch's allocator holds, is never evicted. Managed memory is the only memory the driver may move to the CPU when a device allocation needs room. At the logprob peak that leaves UCCL's block as the only candidate, whatever its size. When `combine` then reads it, the GPU faults, and the driver needs free GPU memory to bring it back, which is exactly what is missing at that moment. A single-GPU reproduction can confirm this: prefetch a managed block to the GPU, fill HBM with `cudaMalloc`, then launch a kernel that reads the block.

The single-GPU reproduction (`backends/nemo-rl/uvm_evict_test.cu`, run with `uvm_evict_test.sh`, 2026-10-17 on nid006270 and nid006129) settles the cause. It builds UCCL's structure the way `uccl_ep.cc` does, with 32 40-byte handles and the table of pointers to them in `cudaMallocManaged` memory, initialised on the host and prefetched to the GPU, and reads it from a kernel as `combine` does. Filling the GPU with `cudaMalloc` between two kernels did not break UCCL's allocation; reads with 6 MB left were correct, and `CUDA_MANAGED_FORCE_DEVICE_ALLOC=1` changed nothing. Adding preferred-location and accessed-by hints for the GPU made the first read after the fill fail with "an illegal memory access was encountered" (700) after 205 ms, so those hints are no fix. The decisive variant fills the GPU while a kernel keeps reading the table, as in training, where PyTorch allocates while UCCL's kernels run. With UCCL's unchanged allocation the reader died with the same error within 0.5 s, as soon as the GPU was full. With the table and handles in `cudaMalloc` memory it ran the full 20 s, about two billion reads, all correct. Managed memory is the only memory the driver may evict from the GPU, and it evicts in 2 MB units, so when a `cudaMalloc` finds the GPU full it takes UCCL's block, small as the table is. A kernel reading the table at that moment cannot get it back and takes a fatal MMU fault. This matches every observation: the crashes fall in the logprob pass, the memory peak; they are intermittent, because the allocator must need the very last megabytes while a UCCL kernel runs; and the 4K runs, with the higher peak, crash most. The fix is `apertus2/patches/uccl/0001-ep-keep-the-D2H-handle-table-in-device-memory.patch` (against UCCL 540cc775): build the handles on the host and copy them to `cudaMalloc` memory. UCCL has no other managed allocation; each dump shows exactly one managed section. It needs a UCCL rebuild.

A correction to the reading of the 10-second HBM samples. The 4K trace's crash shows the same pattern as 3682994's. At 18:01:40, four seconds after the logprob pass began and four seconds before the fault, the faulting GPU (NUMA node 4 on nid007592) held 73.8 GiB; at 18:01:50 it held 92.1 GiB, while the node's other three GPUs sat at 57 GiB. I had read such post-crash values as an effect of the crash. But once the fault is raised the CUDA context accepts no further allocations, so the climb most likely happened in the seconds before the fault, at the start of the logprob pass. The samples are simply too sparse to catch the peak, and none of the crashes is evidence of a crash without memory pressure. Much of a "full" GPU is PyTorch's cache rather than live tensors (for example 50 GiB allocated against 58 GiB reserved when the logprob pass starts). Without the eviction, a `cudaMalloc` at the limit would have made PyTorch return its cache to the driver and retry, a slowdown rather than an out-of-memory error.

The save itself allocates nothing that outlives it; afterwards, the optimizer offload before the next logprob pass frees less than at every earlier step, by 5.5-6.6 GiB on most ranks and 11.6 GiB on ranks 14 and 15. Reading Megatron's and NVRx 0.6.0's synchronous save path did not show the holder. NeMo-RL patch 0007 avoids it: when `offload_optimizer_for_logprob` is set, the save moves the optimizer state to the CPU instead of to the GPU, the save writes it from there, and `prepare_for_training` later brings it back as new GPU tensors. The held copies then stay in host memory (about 25-35 GiB per trainer node per save, out of 800 GiB). Rank 0 also logs `[ckpt_holders]` after each save, with the referrers of its largest optimizer-state tensor and the number of other tensors sharing its storage, to find the holder.
